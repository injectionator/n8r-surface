# Shared-core parity release candidate

Package **0.1.0-experimental.6** and Researcher skill **0.1.17** prepare the
shared CycloneDX implementation already consumed by Labs for distribution.
The published version remains `.5` / skill `0.1.16`; this candidate is not a
registry release or a marketplace promotion. Preparation is authorized under
[issue #92](https://github.com/injectionator/n8r-surface/issues/92).

## Shared implementation, independent releases

**Surface and Labs reuse one maintained implementation of Surface validation,
views and revision storage. They do not maintain parallel copies of that logic.**
The public [`@n8r/surface/cyclonedx` entry](../../src/cyclonedx.ts) exports the
shared validation, rendering and persistence functions. Labs imports that entry
from a pinned Surface package, using the local dependency alias
`@n8r/surface-cyclonedx`; the alias is not a separate implementation.

The standalone skill's `surface.mjs` is a generated bundle of those same source
modules, built by [build-skill.mjs](../../scripts/build-skill.mjs) through
[skill-surface-cli.ts](../../src/skill-surface-cli.ts). Bundling makes it usable
without a package installation; generated delivery copies are not independently
edited source. `npm run check:skill` checks exact generated bytes against source.
Labs also reads the Researcher instructions from its pinned Surface package.
Host orchestration, access permissions and application integration remain separate;
this is not a claim that both products share a complete research-session engine.

**Shared source does not require synchronized releases.** Labs pins a reviewed
Surface artifact and can integrate it before or after the corresponding public
Surface release. Surface can release without requiring Labs to upgrade. Each
consumer chooses when to adopt a revision and verifies its own integration;
recorded source revisions and artifact digests identify what it actually uses.
Changes to shared semantics belong in Surface, while host-specific behavior
belongs in the consuming product. A pinned artifact is not a fork to maintain.

## Release decisions and recovery

Review readiness, merge, marketplace promotion and npm publication are separate
decisions. Keep the preparation PR draft. After
approval, build the publishable archive from the reviewed clean release commit
on `main`, with a new permanent annotated `v0.1.0-experimental.6` tag. Local
private candidates are not the publishable bytes; retain each report separately.

The manual release workflow is guarded for `.6`. After explicit authorization,
follow the [previous staged release procedure](npm-release.md#preparation-and-publication)
using **v0.1.0-experimental.6** for every operation. `prepare` creates the fresh
publishable archive and draft release once; `stage` submits those retained bytes
for maintainer 2FA; `verify` independently checks the published bytes. Never run
these operations for `.5` again. No workflow dispatch is part of local preparation.

Check current registry state before staging. An existing version must be verified,
never republished. On partial failure retain the exact original assets and follow
the [recovery procedure](npm-release.md#prepare-and-stage-retained-artifacts);
never replace an archive silently. Registry signatures, signed provenance,
source/workflow identity, installed registry readback and final immutable release
verification remain pending until publication. Do not promote `latest`.
